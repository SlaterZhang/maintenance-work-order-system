# 团队协作启动指南

## 目标

四个人可以并行开发，但任何时刻都应能回答：

1. 这个任务由谁负责？
2. 它对应哪条需求？
3. 是否改变了其他成员依赖的字段或行为？
4. 如何验证完成，失败时如何回滚？

## 第 0 天：一次性准备

仓库负责人完成：

1. 邀请另外三名成员为 Collaborator，均使用自己的 GitHub 账号；
2. 将本规范包放入仓库根目录；
3. 执行 `scripts/bootstrap.ps1`，生成 `.github/CODEOWNERS`；
4. 推送初始化 PR；
5. 为 `main` 启用分支保护；
6. 在 GitHub Issues 中录入本迭代任务；
7. A/B/C 确认业务语义，D 检查契约完整性和可测试性，四人共同确认 `contracts/`。

## 每日节奏

建议每天用 10 分钟同步一次，只讨论四件事：

- 昨天合并了什么；
- 今天准备完成哪个 Issue；
- 是否要修改公共契约；
- 当前阻塞由谁在何时处理。

结论写入对应 Issue 或 PR，不以聊天记录作为唯一依据。

## 看板状态

可使用 GitHub Projects，最少保留以下状态：

| 状态 | 进入条件 | 离开条件 |
| --- | --- | --- |
| Backlog | 需求已记录但未细化 | 负责人和验收条件明确 |
| Ready | 可直接开发、无未决契约 | 成员创建分支并开始处理 |
| In progress | 已有负责人和工作分支 | 创建 Draft PR |
| Review | PR 可运行且自测完成 | 批准并合并，或退回修改 |
| Done | 已合入 `main` 且检查通过 | 不再移动 |

每人同时最多保留一个主要 In progress 任务，避免四个人都产生大量半成品。

## 一项功能的完整例子

以 C-FR-14“备件查询”为例：

1. C 创建功能 Issue，写明查询条件、输出字段、无库存和接口失败时的行为；
2. 若需要 A 提供设备型号，C 创建契约变更 Issue，与 A 确认字段；
3. C 从 `main` 创建 `feat/c-C-FR-14-spare-query`；
4. 先补充契约示例，再实现查询和测试；
5. C 创建 Draft PR，请求 A 评审设备字段、D 评审契约与自动测试；
6. 自动检查和评审通过后 Squash merge；
7. C 在 Issue 中附测试证据并关闭任务。

## 遇到不一致时

不要让某一方“临时兼容一下”后继续各写各的。按以下顺序处理：

1. 暂停合并相关 PR；
2. 在契约变更 Issue 中写出四方当前理解，由 D 汇总差异但不替代业务负责人决策；
3. 选定唯一字段名、类型、枚举和值域；
4. 先合并契约与示例；
5. 再分别修改提供方和调用方；
6. 运行端到端场景并保存结果。
