# 详细接口约定与联调手册

> 基线版本：2.0.0  
> 生效范围：成员 A、B、C、D 的前后端开发、模块联调和课程演示  
> 机器可读契约：contracts/openapi.yaml

## 1. 已冻结的技术约定

以下内容是四个人开始开发时的默认答案。除非提交契约变更 PR 并由提供方、调用方共同确认，否则不得各自修改。

| 项目 | 统一约定 |
| --- | --- |
| API 主版本 | /api/v1 |
| 数据格式 | application/json; charset=utf-8 |
| JSON 字段 | lower camelCase，例如 equipmentId |
| 时间 | RFC 3339 UTC，例如 2026-09-17T08:30:00Z |
| 分页 | page 从 1 开始，pageSize 默认 20、最大 100 |
| 前端鉴权 | Authorization: Bearer JWT |
| 服务间鉴权 | X-Internal-Token |
| 链路追踪 | X-Trace-Id；服务间调用必传并沿用 |
| 写操作幂等 | Idempotency-Key，值为 UUID |
| 并发修改 | 请求传 expectedVersion，不一致返回 409 |
| 成功响应 | 直接返回契约中的业务对象，不再额外套 data |
| 失败响应 | 统一使用 ErrorResponse，不得用 HTTP 200 表示失败 |
| 空值 | 可为空的字段必须显式返回 null，不得用空字符串替代 |

## 3. 数据所有权和禁止事项

| 数据 | 唯一权威方 | 其他模块允许保存的内容 |
| --- | --- | --- |
| 设备档案、EquipmentId、设备当前状态 | A | B/C 保存 ID；C 可保存建单时的设备名称快照 |
| 健康结果、预警、WarningId | B | C 保存与工单关联所需的预警快照 |
| 工单、备件、OrderId、SpareRequestId | C | A/B 保存关联 ID 和本模块处理结果 |
| 用户、角色、权限、通知任务 | D | A/B/C 只保存业务记录中的 UserId |
| 公共枚举、接口定义 | 四人共同确认，D 维护校验 | 各模块生成 DTO 或类型，但不能另起一套值 |

严禁跨模块直接查询或修改对方数据库。跨模块只通过本手册和 contracts/ 中定义的接口交换数据。

## 6. 风险等级与优先级

第一版统一使用以下映射，B 不得返回一套风险，C 再自行解释另一套优先级。

| 健康分 | 风险等级 | 自动工单 | 工单优先级 |
| --- | --- | --- | --- |
| [80, 100] | LOW | 否 | P4 |
| [60, 80) | MEDIUM | 否 | P3 |
| [40, 60) | HIGH | 是 | P2 |
| [0, 40) | CRITICAL | 是 | P1 |

B 可以自行实现规则评分或异常检测算法，但输出必须满足这个分段。B 只把 HIGH、CRITICAL 的 WarningRaised 发送给 C。

## 7. 工单状态机

所有工单变更统一调用：

    POST /api/v1/work-orders/{orderId}/commands

请求公共字段为 action、operatorId、expectedVersion，其余字段按下表决定。

| 当前状态 | action | 目标状态 | 允许角色 | 附加要求 |
| --- | --- | --- | --- | --- |
| PENDING_CONFIRMATION | CONFIRM | PENDING_ASSIGNMENT | 维修主管、管理员 | 无 |
| PENDING_ASSIGNMENT | ASSIGN | PENDING_ACCEPTANCE | 维修主管、管理员 | assigneeId 必填 |
| PENDING_ACCEPTANCE | ACCEPT | PENDING_MAINTENANCE | 被指派维修人员 | operatorId 等于 assigneeId |
| PENDING_MAINTENANCE | START | MAINTAINING | 被指派维修人员 | C 向 A 发 MAINTAINING |
| MAINTAINING | WAIT_FOR_PARTS | WAITING_PARTS | 被指派维修人员 | comment 说明缺件 |
| WAITING_PARTS | RESUME | MAINTAINING | 被指派维修人员 | 备件已满足 |
| MAINTAINING | SUBMIT_FOR_INSPECTION | PENDING_INSPECTION | 被指派维修人员 | conclusion 必填；C 向 A 发 TRIAL_RUNNING |
| PENDING_INSPECTION | REJECT_INSPECTION | MAINTAINING | 验收员、主管 | comment 必填；C 向 A 发 MAINTAINING |
| PENDING_INSPECTION | PASS_INSPECTION | COMPLETED | 验收员、主管 | C 向 A 发 RUNNING，向 B 发维修结论 |
| 确认、待派发或待接单 | CANCEL | CANCELLED | 维修主管、管理员 | comment 必填 |

服务端必须拒绝表中没有列出的迁移，并返回：

    {
      "code": "INVALID_STATE_TRANSITION",
      "message": "PENDING_ASSIGNMENT 状态不能执行 START",
      "traceId": "trace-20260917-001",
      "timestamp": "2026-09-17T08:40:00Z",
      "details": []
    }

不得允许前端直接提交目标 status。状态只能由命令和服务端规则产生。

## 8. 备件申请状态机与库存规则

| 当前状态 | action | 目标状态 | 数量规则 |
| --- | --- | --- | --- |
| PENDING_APPROVAL | APPROVE | APPROVED | quantity 必填，且不大于申请量 |
| PENDING_APPROVAL | REJECT | REJECTED | comment 必填 |
| APPROVED | RESERVE | RESERVED | 可用库存必须不少于批准量 |
| RESERVED | ISSUE | ISSUED | quantity 必填，不大于批准量 |
| ISSUED | RETURN | PARTIALLY_RETURNED 或 CLOSED | quantity 必填，累计退回量不大于领用量 |
| ISSUED、PARTIALLY_RETURNED | CLOSE | CLOSED | 确认不再退回 |
| PENDING_APPROVAL、APPROVED、RESERVED | CANCEL | CANCELLED | 已预留时必须同时释放库存 |

必须满足：

    availableQuantity = onHandQuantity - reservedQuantity
    0 <= returnedQuantity <= issuedQuantity <= approvedQuantity <= requestedQuantity

库存变动必须产生不可覆盖的流水。不得只修改备件表上的最终数量而不保留原因、工单、操作者和时间。

## 9. 三个跨模块事件

事件都使用相同包络：

    {
      "eventId": "2fbc3b4c-7ec1-4eb6-a6b7-6ebae174d001",
      "eventType": "WarningRaised",
      "schemaVersion": "2.0",
      "occurredAt": "2026-09-17T08:30:00Z",
      "sourceMember": "MEMBER_B",
      "traceId": "trace-20260917-001",
      "payload": {}
    }

| 事件 | 发送方 → 接收方 | 接收端路径 | 幂等依据 |
| --- | --- | --- | --- |
| WarningRaised | B → C | /api/v1/integration/warning-events | eventId；warningId 还必须唯一关联有效工单 |
| EquipmentStatusChanged | C → A | /api/v1/integration/equipment-status-events | eventId |
| MaintenanceConclusionReported | C → B | /api/v1/integration/maintenance-conclusions | eventId；同一 orderId 的最终结论不可被旧版本覆盖 |

同一事件重试时，URL、eventId、Idempotency-Key 和请求体必须完全相同。接收方应返回原处理结果并令 duplicate=true，不得重复建单、重复扣库存或重复通知。

## 10. 关键业务规则

1. C 接到预警事件后，先调用 A 的设备查询；设备不存在时不建单并返回 404。
2. 同一 warningId 最多关联一张未取消工单。
3. C 建单时保存 equipmentNameSnapshot，但不得把它当成设备当前权威名称。
4. A 接收设备状态事件时，仅接受契约枚举中的状态。
5. B 接到维修结论后：
   - RECOVERED 且 effective=true：预警变为 RESOLVED；
   - PARTIALLY_RECOVERED：预警保留为 ACKNOWLEDGED；
   - NOT_RECOVERED：预警保持打开并允许升级风险。
6. 工单完成前，C 必须已经保存维修结论。
7. 任何模块调用 D 的通知接口失败时，不回滚已成功的核心业务；记录待重试通知。
8. 前端隐藏按钮不能代替服务端权限检查。

## 11. 幂等与并发的精确定义

### 11.1 幂等键

- 同一个 Idempotency-Key，加上相同方法、路径和请求体：返回第一次处理的状态码和响应体；
- 同一个 Idempotency-Key，但请求体不同：返回 409，错误码 IDEMPOTENCY_CONFLICT；
- 建议保存幂等记录至少 24 小时；
- 查询接口和登录接口不需要幂等键。

### 11.2 乐观锁

- 可修改实体均返回 version；
- 命令或更新请求提交 expectedVersion；
- expectedVersion 不等于数据库当前版本时返回 409，错误码 VERSION_CONFLICT；
- 客户端收到冲突后重新查询，不得自动覆盖新数据。

## 12. 统一错误码

| HTTP | code | 使用场景 |
| --- | --- | --- |
| 400 | VALIDATION_ERROR | 缺字段、类型、长度、格式或枚举错误 |
| 401 | AUTH_INVALID_CREDENTIALS | 用户名或密码错误 |
| 401 | AUTH_TOKEN_INVALID | JWT 或内部令牌无效 |
| 403 | PERMISSION_DENIED | 当前角色无权执行 |
| 404 | EQUIPMENT_NOT_FOUND | 设备不存在 |
| 404 | WARNING_NOT_FOUND | 预警不存在 |
| 404 | WORK_ORDER_NOT_FOUND | 工单不存在 |
| 404 | SPARE_REQUEST_NOT_FOUND | 备件申请不存在 |
| 409 | VERSION_CONFLICT | expectedVersion 过期 |
| 409 | IDEMPOTENCY_CONFLICT | 同一幂等键对应不同请求 |
| 409 | INVALID_STATE_TRANSITION | 当前状态不允许该命令 |
| 409 | WARNING_ALREADY_LINKED | 预警已关联有效工单 |
| 409 | INSUFFICIENT_STOCK | 可用库存不足 |
| 422 | WARNING_LEVEL_NOT_ACTIONABLE | LOW/MEDIUM 预警请求自动建单 |
| 500 | INTERNAL_ERROR | 未预期服务错误 |

所有错误体都必须包含 code、message、traceId、timestamp 和 details。

## 14. 高风险自动派修的完整调用顺序

1. A 接收或生成监测样本并保存。
2. A 调用 B 的 POST /api/v1/health-evaluations。
3. B 返回健康分和风险等级；若为 HIGH/CRITICAL，生成唯一 WarningId。
4. B 调用 C 的 POST /api/v1/integration/warning-events。
5. C 按 eventId 去重并调用 A 查询设备。
6. C 按风险映射创建 PENDING_CONFIRMATION 工单，返回 OrderId。
7. C 调用 D 提交 WORK_ORDER_CREATED 通知。
8. 工单 START 时 C 向 A 发送 MAINTAINING。
9. 提交验收时 C 向 A 发送 TRIAL_RUNNING。
10. 验收通过时 C 向 A 发送 RUNNING，并向 B 发送维修结论。

这十步必须沿用同一个 X-Trace-Id。局部调用失败时记录待重试任务，不重新生成业务 ID。

## 17. 契约变更规则

以下任一变化都必须先提“契约变更”Issue：

- 修改路径、方法、字段名、类型、必填性或单位；
- 新增或删除枚举值；
- 修改状态迁移、风险映射或错误码；
- 修改某个 ID 的生成方；
- 让调用方开始依赖之前未承诺的字段。

PR 中必须同时更新：

1. contracts/openapi.yaml；
2. contracts/shared-enums.json；
3. 受影响的 JSON Schema 和示例；
4. contracts/http/local-api.http；
5. 自动检查或测试；
6. 本手册中的相关表格。
