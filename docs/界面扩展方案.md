# 界面扩展方案：从「两个页面」到「企业级运维平台」

> 背景：当前看板只有「首页看板 + 维修工单」两个视图，`web/` 共 1737 行，信息密度低，
> 给人的印象是「一个任务调度工具」而不是「一套运维平台」。
> 本方案规划如何把它扩展成**多模块、多页面、每个页面都有明确职责说明**的企业级界面。

---

## 一、为什么现在显得"简单"

| 现象 | 根因 |
|---|---|
| 只有 2 个导航项 | 信息架构没分层——把「设备、预警、工单、备件、权限」全塞进首页看板 |
| 首页信息密度低 | 4 个统计卡 + 2 个列表，没有对比、排名、趋势、分布 |
| 功能不可发现 | 已有接口（备件、权限、通知、集成）**后端全都有，前端没入口** |
| 缺少"专业感" | 没有侧边栏分级导航、没有面包屑、没有页面级说明、没有详情 Tab |
| 感觉不像平台 | 没有"系统"层面的页面：集成监控、模型管理、数据质量、报表 |

**关键结论：后端能力远超前端呈现。** 契约里已有 **23 条路径 / 27 个操作**，
但前端只用了其中约 10 个。扩展界面主要是「把已有能力暴露出来」，
真正的开发量比看上去小得多。

---

## 二、信息架构（IA）

按**使用者视角**分组，而不是按微服务 A/B/C/D 分组——后者是技术视角，用户看不懂。

```
┌─ 运营总览
│   ├─ 驾驶舱首页          ← 已有（增强）
│   └─ 实时监控大屏        ← 新增
│
├─ 设备管理
│   ├─ 设备资产台账        ← 已有（增强为多列可筛选表格）
│   ├─ 设备详情            ← 已有（重构为 6 个 Tab）
│   └─ 设备档案/铭牌       ← 新增
│
├─ 健康与预警
│   ├─ 健康评估中心        ← 新增
│   ├─ 预警中心            ← 已有（增强）
│   └─ 预警规则阈值        ← 新增
│
├─ 维修管理
│   ├─ 工单看板（Kanban）  ← 新增
│   ├─ 工单列表            ← 已有
│   └─ 工单详情/时间线     ← 新增
│
├─ 备件管理
│   ├─ 备件库存            ← 新增
│   └─ 领用申请            ← 新增
│
├─ 智能分析（演进中）
│   ├─ 异常检测            ← 演进
│   ├─ 寿命预测 RUL        ← 演进
│   ├─ 归因诊断 SHAP       ← 演进
│   └─ 知识库助手 RAG      ← 演进
│
├─ 模型与数据（演进中）
│   ├─ 模型管理/双轨对账   ← 演进
│   ├─ 数据质量与漂移      ← 演进
│   └─ 数据集与特征        ← 演进
│
└─ 系统管理
    ├─ 组织与权限 RBAC     ← 已有接口（前端新增）
    ├─ 通知中心            ← 已有接口（前端新增）
    ├─ 系统集成监控        ← 已有接口（前端新增）
    └─ 审计日志            ← 已有数据（前端新增）
```

**设计原则：演进中的模块照样放进导航，但打「演进中」标签并做说明页。**
这样界面立刻显得丰富，同时**不撒谎**——点进去能看到规划说明与占位骨架，
而不是空白或假数据假装能用。

## 三、页面清单与实现映射

### 3.1 立即可做（后端接口已存在，只差前端）

| 页面 | 用到的真实接口 | 工作量 |
|---|---|---|
| 设备资产台账 | `GET /api/v1/equipment` | 1 天 |
| 设备详情（6 Tab） | `GET /equipment/{id}`、`GET /equipment/{id}/telemetry` | 2 天 |
| 预警中心 | `GET /api/v1/warnings`、`GET /warnings/{id}`、`POST /warnings/{id}/acknowledgements` | 1.5 天 |
| 健康评估中心 | `GET /health-evaluations/latest` + 评估历史 | 1.5 天 |
| 工单看板 Kanban | `GET /api/v1/work-orders`、`POST /{id}/commands` | 2 天 |
| 备件库存 | `GET /api/v1/spare-parts` | 1 天 |
| 领用申请 | `POST /work-orders/{id}/spare-requests`、`POST /spare-requests/{id}/commands` | 1.5 天 |
| 组织与权限 | `GET /api/v1/users`、`GET /users/{id}/access-context` | 1 天 |
| 通知中心 | `POST /api/v1/notifications` + 列表 | 0.5 天 |
| 系统集成监控 | 各服务 `/health` + 契约元数据 | 1 天 |
| 审计日志 | C 服务 `audit_log`（需新增查询接口） | 1 天 |

小计约 **14 人天**，全部有真实接口支撑，**零契约破坏**。

### 3.2 需要小幅扩展（新增只读查询接口）

| 页面 | 需要的接口 | 说明 |
|---|---|---|
| 审计日志 | `GET /api/v1/audit-logs?orderId=` | 数据已在 `audit_log` 表，只缺查询入口 |
| 评估历史 | `GET /api/v1/health-evaluations?equipmentId=&limit=` | B 已有 `health_evaluation` 表 |
| 设备档案 | `GET /api/v1/equipment/{id}/profile` | 铭牌/厂商/安装日期等字段需扩模型 |
| 实时监控大屏 | SSE 或轮询 `/telemetry?limit=1` | 轮询即可，无需新协议 |

新增接口都属**向后兼容的只读扩展**，走正常契约变更流程即可（新增 path + schema）。

### 3.3 演进模块（占位骨架 + 说明页）

这些页面**先做信息设计**，展示"将来长什么样"：
- 异常检测：异常事件列表、重建误差时间轴、阈值带
- 寿命预测：RUL 仪表盘、P10/P50/P90 区间、触阈值倒计时
- 归因诊断：SHAP 特征贡献瀑布图、传感器热力时段
- 知识库助手：对话式检索 + 引用来源卡片
- 模型管理：规则 vs 影子双轨对账表（一致率/漏报/误报）、版本台账
- 数据质量：PSI/KL/KS 漂移曲线、告警阈值带

每个页面上方有**统一样式的说明条**：这个大屏做什么、当前状态、依赖哪份规划。
用户点进去不会觉得被骗，反而会觉得"这套东西是有路线图的"。

## 四、视觉与交互升级

1. **左侧固定侧边栏**（替代顶部 2 个按钮）
   - 分组折叠、图标 + 名称、当前项高亮、演进项带 `β` 角标
   - 可收起为图标条
2. **顶栏**：面包屑 + 全局搜索 + 通知铃铛（带角标）+ 用户菜单 + 环境切换
3. **页面级说明条**：每页顶部一行小字说明"这个页面解决什么问题、数据来自哪个服务"
4. **详情页 Tab 化**：概览 / 遥测 / 健康 / 预警 / 工单 / 档案
5. **卡片化 + 密度提升**：KPI 卡、排名榜、分布环、趋势迷你图（sparkline）
6. **状态色系统**：沿用现有 `--green/--yellow/--red` 语义，新增 `--purple` 标识演进内容
7. **空状态与骨架屏**：真数据为空时给明确指引（如"还没有预警记录，去注入异常试试"）

## 五、实施顺序（建议）

**第 1 波（3 天）—— 框架先行**
搭侧边栏 + 路由 + 页面说明条 + 把现有 2 个页面搬进新框架。此时界面结构已"像平台"。

组织权限、通知中心、集成监控、审计日志。

## 六、原型说明

`web/prototype/platform.html` 是可交互的**视觉原型**（单文件，零构建，202 KB）：

- 左侧完整导航（8 大分组，含演进分组）
- **24 个页面**均已绘制，含静态演示数据
- 每页带说明条，明确标注「已实现（真实接口）」或「演进中（规划）」
- 用真实设计令牌（配色、字体、圆角、间距）与现有看板保持一致
- **不连接后端**，纯静态，用于确认信息架构与视觉方向
- 页面切换靠导航点击（内部 `go('pid')`），便于演示与截图

在线访问：`http://192.168.0.64:8888/prototype/platform.html`（服务器已部署）
本地亦可直接双击打开（纯静态，`file://` 同样可用）。

确认方向后再按第五节顺序落地真实页面。

## 七、风险与边界

- **不要把演进模块画得和已实现一样**——必须用 `β` 角标 + 说明条区分，
  否则演示时被追问"这个功能怎么用"会很尴尬。
- **不要为了丰富而堆假数据**——原型里的数字标注为"演示数据"，
  真实页面接真接口。空状态要设计好。
- **侧边栏不要超过 3 层**——超过就说明信息架构该重组了。
- **移动端**：侧边栏在窄屏折叠为抽屉；大屏页面单独适配横屏。

### 自检中修正的真实错误（避免原型的枚举与契约不符）

原型初稿凭印象写了枚举值，逐条比对 `contracts/shared-enums.json` 后修正：

| 位置 | 错误值 | 契约真值 | 性质 |
|---|---|---|---|
| 设备状态 | `WAIT_FOR_PARTS`（当作设备状态用） | `TRIAL_RUNNING` | **根本不存在此设备状态** |
| 设备状态标签 | 缺少 `WARNING` / `TRIAL_RUNNING` | `equipmentStatus` 共 5 项 | 漏项 |
| 权限码 | `EQUIPMENT_WRITE` | `EQUIPMENT_MANAGE` | 名称不符 |
| 权限码 | 缺少 `ADMIN_ALL` / `TELEMETRY_READ` | 21 项完整清单 | 漏项 |
| 权限码 | `EVALUATION_SUBMIT` | 不存在（评估由 A 触发） | **虚构权限** |
| 权限码 | `USER_READ` | `USER_ACCESS_READ` | 名称不符 |
| 工单动作 | `WORK_ORDER_MAINTENANCE` | `WORK_ORDER_MAINTAIN` | 名称不符 |
| 工单动作 | 缺少 `RESUME` | `WAITING_PARTS → MAINTAINING` 靠 RESUME | 漏项 |
| 备件状态 | `OUT_OF_STOCK` / `RETURNED` | `REJECTED` / `PARTIALLY_RETURNED` | **虚构状态** |
| 风险等级 | `LOW 正常` / `MEDIUM 关注` | 契约 `displayName` = 低 / 中 / 高 / 严重 | 文案不符 |

**教训：界面原型里的任何枚举值都必须从契约文件读取，不能凭印象写。**
这些错误在演示时会被懂行的评审一眼看穿（"你们设备还能是待备件状态？"），
而修正成本几乎为零——只要 `grep contracts/shared-enums.json`。

### 技术验证

- `node --check` 提取内联 JS → **exit 0**（语法通过）
- `Runtime.evaluate` 遍历 `Object.keys(PAGES)` 调用全部 24 个渲染函数 → **0 报错**，累计 HTML 长度 291,063 字符
- 无头 Chromium `--headless=new` + CDP `Page.captureScreenshot(captureBeyondViewport)` → 24 张全页 PNG 逐张 `read_image` 目检
- nginx 静态服务：`GET /prototype/platform.html` → **200**，`text/html`，204,822 字节
- 文件权限 644（符合 `AGENTS.md` 对 `web/` 下静态文件的要求，否则 nginx 403）

### 构建期修正的渲染缺陷

1. 监控大屏过空（仅 4 KPI + 3 图）→ 补设备状态矩阵、实时事件流、4 组统计卡
2. RUL 页与异常检测页用 `.ph` 斜纹占位块 → 改为自绘 SVG 概率分布图 / 重建误差时间轴
3. 归因诊断热力图嵌在 flex 居中容器里被压缩 → 容器改 `display:block;height:auto`
4. 工单详情右列过长导致左列大片空白 → 补动作面板、SLA 规则、并发幂等说明、同类历史工单、故障知识沉淀、通知记录
5. `.li .l2` 是 `display:flex`，长文本会被渲染成竖排单字 → 改用内联样式 div
6. 卡片网格里误插入 `mt` 卡片导致嵌套错位 → 移到网格之外
