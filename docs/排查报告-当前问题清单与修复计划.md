## 二、P0 致命问题（演示会当场失败，已实测复现）

### P0-1 健康评估写入 500 —— 核心链路断裂【根因：数据库迁移缺失】

**证据链（全部实测）**：

1. 生产库 `member_b.db` 的 `health_evaluation` 表结构（PRAGMA 实查）：
   ```
   response_body  TEXT  NOT NULL   ← 旧结构的 JSON 落库字段
   health_score / risk_level / suspected_fault / ...  ← 今天新加的列（均可空）
   ```
2. 今天的提交把 ORM 模型改成了结构化列（`models.py` 的 `HealthEvaluation` 已无 `response_body`），INSERT 语句不再包含该字段 → 违反旧表 `NOT NULL` 约束：
   ```
   sqlite3.IntegrityError: NOT NULL constraint failed: health_evaluation.response_body
   （B 服务日志中当天出现 26 次）
   ```
3. **接口实测**：`POST /api/v1/health-evaluations`（正常值样本）→ **HTTP 500**
4. **官方 e2e 脚本实测**：`scripts/e2e_demo.py` 在 E2E-01 第 2 步即失败：
   ```
   × 健康评估失败 HTTP 500: {"code":"INTERNAL_ERROR","message":"当日 WarningId 序号分配失败..."}
   ```
5. B 服务 179 项测试**全绿**——因为测试用全新建库（新结构），生产库是旧结构。**测试通过 ≠ 生产可用**，这个断层就是根因的化身。

**错误面具的迷惑性（排障陷阱）**：同一个 NOT NULL 根因，异常值样本（走预警路径）报"**当日 WarningId 序号分配失败**"——因为评估对象 add 后的 autoflush 在 `_obtain_warning` 的查询里触发 IntegrityError，被序号分配的 `except IntegrityError: continue` 循环吞掉，重试耗尽后抛出误导性文案；正常值样本（不走预警路径）则直接裸报 "Internal Server Error"。**如果按报错文案去查"序号分配"，会完全查错方向。**

**连锁后果（这就是"demo 界面问题很大"的源头）**：
- 注入异常 → 评估 500 → 预警不生成 → **自动建单不发生** → 后面全链路没戏；
- 恢复正常 → 评估 500 → 健康度永不更新 → 设备红/黄状态残留；
- 前端为了绕过它打了三层补丁（`latestEvaluation` 客户端缓存、healthMap 覆盖、`setTimeout` 强刷——见 dashboard.html L844-865），补丁又引入新问题（见 P2）。

**历史脉络**：git 近 10 条提交里有 6 条 fix 都在与这个故障搏斗（`恢复数据后健康度不更新`、`引入latestEvaluation优先缓存`、`恢复数据后触发 B 重新评估`、`健康评估 API 修复数据库字段解析`……），但都在修"症状"，没人修"根因"。工作区目前还留着一个未提交的 raw SQL 改动（`health_evaluations.py`），它只修了**读**路径，**写**路径仍然断着。

### P0-2 看板轮询 401 死循环 —— `latest` 接口用错鉴权依赖

- `GET /api/v1/health-evaluations/latest`（今天为看板新加的接口）挂了 `internal_token` 依赖（要求 `X-Internal-Token`，`health_evaluations.py` L50）；
- 但前端 `refreshDashboard()` 用的是 `authHeaders()`（只有 Bearer + X-User-Id，dashboard.html L579）；
- **实测**：带内部令牌 → 200；模拟浏览器 → **401 "内部令牌无效"**；
- 后果：设备页每 5 秒 × 每台设备发一次注定 401 的请求（B 日志已被刷屏），"最新健康评估"覆盖功能**从上线起就没通过浏览器成功过一次**。日志里 401 风暴即此。

### P0-3 遗留脏数据影响演示

- C 库有 2 条今天卡在 `PENDING_CONFIRMATION` 的工单（10:22 / 10:44 产生）＋ 6 条历史已完成/取消单混在列表里；
- B 库有 1 条 **OPEN 状态的残留预警**（EQ-000002，10:44）——它已无对应工单流程，会一直挂在预警列表里；
- 演示前没有"重置演示数据"能力，越演越乱（你已确认**清库重建**方向）。

## 三、P1 架构与安全问题（评委一问就破）

### P1-1 鉴权形同虚设：X-User-Id 直通

- B/C 服务完全信任浏览器直接发来的 `X-User-Id` 头（`fault-warning/.../deps.py` L95-111，注释写"真实部署中由网关 D 在 JWT 校验后注入"——**但实际部署没有网关，浏览器就是直接调用方**）；
- D 服务认真签发了 JWT（HS256、2 小时有效），但 B/C **从不校验**它——前端把 token 存了 localStorage 也基本白存；
- 后果：**任何人打开 F12 改一个头就能冒充任何角色**，7 角色 RBAC 的"权限隔离"只是前端按钮显隐，答辩演示"反例验证"环节如果评委现场改头试一下，整个权限故事就塌了。

### P1-2 内部令牌硬编码在浏览器里

- `dashboard.html` L331：`const INTERNAL_TOKEN = "dev-internal-token-change-me";`
- 浏览器以"内部服务"身份直接调 A/B 的内部接口（注遥测、评估），等于把服务间鉴权向全世界公开；`console.log` 还把 token 前缀打进控制台（L422-425）；
- 演示"注入控制台"是道具可以接受，但**道具应该有专门入口**（比如 D 提供带权限的演示接口），而不是把内部令牌发放给所有浏览器。

### P1-3 前端代跑业务闭环（README 叙事与实现不符）

- README 宣称"C→A 发设备恢复事件、C→B 维修结论关闭预警"；实际**设备恢复**是前端在验收通过后自己向 A 注 RECOVERY 遥测、自己向 B 发评估（dashboard.html L1206-1305，SUBMIT 和 PASS 两段几乎相同的 50 行重复代码）；
- 评估 500 之后，这段"前端代跑"也必然失败，于是 toast 提示"工单已完成，但设备恢复失败，请手动恢复"——用户看到的就是"系统不灵"；
- 设备健康灯规则（score>70 判绿）在前端硬编码（`equipmentLight` L530-552），与 B 服务规则引擎重复且可能不一致——**业务规则散落两处**，答辩讲"契约驱动/单一事实源"时会被这处打脸。
