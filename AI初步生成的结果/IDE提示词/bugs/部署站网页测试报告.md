## 1. 🔴 严重问题（P0）

### BUG-01 同一设备健康度三处不一致，且差值巨大
- **位置**：驾驶舱首页 `/` · 设备资产台账 `#/assets` · 健康评估中心
- **现象**：
  - 驾驶舱首页「设备实时状态」表： EQ-000001 健康度 **94.7**，驾驶舱概览卡「平均健康度 94.7」
  - 设备资产台账表：EQ-000001 健康度 **30.6**
  - 台账「健康度排行」表：EQ-000001 又是 **94.7**（同一页面内两张表打架）
- **根因推断**：台账页表格读的是 A 服务的 `GET /api/v1/equipment` 裸字段，而排行/驾驶舱读的是 B 服务 `/health-evaluations/latest` 的评分。两套数据源没有对齐口径，前端也没做统一。
- **影响**：设备状态判定错误。94.7 是「健康」，30.6 按页面自己的口径（<60 = 异常）应判「异常」并触发预警。
- **修复建议**：以 B 服务健康评估为唯一真源，A 服务只存状态；或明确区分「静态基线分」与「实时评分」并在页面上标注。

### BUG-02 台账同页两张表数字互相矛盾
- **位置**：`#/assets`
- **现象**：主表 EQ-000001 = 30.6、EQ-000003 = 30.6；下方「健康度排行（后 3 名 · 重点关注）」表里 EQ-000001/002/003 全是 94.7，且「主要风险指标」三行文字完全相同（都是"主轴轴承振动异常"），「建议」也全部是"维持正常监测"。
- **双重问题**：① 数值矛盾；② 排行表是硬编码假数据 —— 所谓"后 3 名"却给 94.7 高分，逻辑自相矛盾。

### BUG-03 台账主表健康度大面积为空（8 台里 5 台是 "—"）
- **位置**：`#/assets`
- **现象**：EQ-000002、004、005、006、007、008 健康度列全部显示 `—`。但驾驶舱首页明明显示「平均健康度 94.7」「3/8 台已评估」，健康评估中心也有数据。
- **影响**：台账作为设备主数据页，最关键的健康度列大面积空值，页面失去可用性。
- **备注**：驾驶舱写「3 / 8 台已评估」，而健康度分布图里「健康（≥80）3、关注 0、异常 0、未评估 5」，合计 8，数字自洽；但台账却拿不到这 3 个分，说明两页取数路径不同。

### BUG-04 工单看板与工单列表的统计口径不一致
- **位置**：`#/kanban` vs `#/orders`
- **现象**：工单看板顶部统计与工单列表统计对不上（未结单数/各状态计数不一致）。
- **影响**：运维人员按看板排队干活，看板数字不准会直接导致漏单。

### BUG-05 备件库存页统计自相矛盾
- **位置**：`#/spares`
- **现象**：
  - 卡片「备件品类 8 / 8 个分类」，但下方「分类库存分布」按分类展开是 8 个品类 —— 这里说的是品类数量不是分类数，措辞误导；
  - 卡片「低于安全库存 **3** / 需立即补货」，但同页另一处「告警项缺口 **11** / 按可用量统计」；表格里"需补货"状态确实 3 行（SP-000002 5/15、SP-000005 4/10、SP-000007 2/3），那 11 是哪来的？无解释。
  - 卡片「可用总量 280 / 扣除预留后」，但表里每一行的「已预留」全是 **0**，且「在库量 = 可用量」8 行全等。既然预留恒为 0，写"扣除预留后"是空话，280 就是在库量合计。
- **影响**：补货决策依赖这些数字，缺口 3 和 11 差 4 倍，无法判断该采多少。

### BUG-06 备件库存「已预留 0」与领用申请「已发料」事实冲突
- **位置**：`#/spares` vs `#/sreq`
- **现象**：领用申请页存在真实流水：
  - SPR-20261012-1587：申请 3 条 → 批准 3 → 已发 3 → 状态「已发料」
  - SPR-20261010-1725：申请 3 个 → 批准 3 → 已发 3 → **已退 2** → 状态「已关单」
  - 按页面自述规则，发料要扣减库存、退料要回冲。
  - 但备件库存页 SP-000002 同步带在库 **5 条**，SPR-20261012-1587 发了 3 条，若初始 8 条则对得上、若初始 5 条则扣减没生效 —— 页面无从验证。更明确的是 SP-000001 主轴轴承在库 41，历史上发过 3 个退过 2 个，账面仍显示 41，**扣减与回冲全都没有体现**。
  - 同时该页「已预留 0 / 待发料占用」，但有 2 条待审批申请挂着。
- **影响**："流水模型可对账"是这套系统的卖点，但前端账面数与流水算不通，对账卖点当场破功。

## 2. 🟠 中等问题（P1）

### BUG-07 通知中心自曝「功能未接通」，还写在演示首页
- **位置**：`#/notify`
- **现象**：页面大字写着「发送记录为空，原因在服务端而不在界面」，并明确列出：B 实现了投递函数但**无 enqueue 调用点**、C 实现了 HTTP 客户端但**无调用点**、A 侧连客户端都没有。页面因此**不提供"发送"按钮**。
- **问题**：把未实现的内部欠账直接展示给用户，且给出了源码路径（`apps/fault-warning/src/application/event_dispatch.py:94` 等）。演示场景下这是减分项。
- **建议**：评委可见的页面改成友好空态（"暂无通知"），欠账清单留在开发文档里。

### BUG-08 通知中心「今日发送 vs 发送总数」双 0，但页面自述有 5 个模板
- **位置**：`#/notify`
- **现象**：今日发送 0、发送总数 0、未接通调用点 2。既然一个通知都没发过，页面却提供了完整的 5 行模板目录表和「渠道与重试策略」表 —— 全部是契约文案，无一条真实数据。整页信息密度极低。

### BUG-09 领用申请 `#/sreq` 页面标题与导航名称不一致
- **位置**：导航「领用申请」→ 页面标题「备件领用申请」→ 但 `#/sreq` 路由访问时面包屑显示"备件管理 / 领用申请"。命名混乱（`sreq` 缩写也不规范，其余页面是 `spares`、`assets` 这类完整词）。

### BUG-10 待审批申请完全重复，疑似幂等失效
- **位置**：`#/sreq`
- **现象**：两条待审批记录指向**同一个工单 + 同一个备件**：
  - SPR-20261012-0114 · WO-20261012-4347 · 主轴轴承 1 个 · 03:43
  - SPR-20261012-0831 · WO-20261012-4347 · 主轴轴承 1 个 · 03:42
  间隔仅 1 分钟，内容完全相同，申请量都是 1，且申请人和审批人都是 USER-D-001。
- **问题**：① 缺重复申请校验；② 若审批人=申请人，等同自己批自己（见 BUG-11）。

### BUG-11 三方分离的治理设计在管理员角色下形同虚设
- **位置**：`#/sreq` 底部「为什么三方分离」
- **现象**：页面强调「申请人不等于审批人」，SPARE_REQUEST / SPARE_APPROVE / SPARE_ISSUE 三码分离。但当前页面自述「当前角色权限：ADMIN_ALL、USER_ACCESS_READ」—— 管理员一个 `ADMIN_ALL` 就通吃全部动作。而列表里两条待审批申请的申请人恰恰是 `USER-D-001`（当前登录人），页面上「批准/驳回」按钮**可点**。
- **影响**：制度设计被超管角色绕过，且没有"禁止自审"的服务端硬约束提示。

### BUG-12 备件库存页「需补货」条目仍可点「领用」
- **位置**：`#/spares`
- **现象**：SP-000002 同步带（5/15）、SP-000005 交流接触器（4/10）、SP-000007 变频器（2/3）状态是"需补货"，但操作列「领用」按钮照样可点，没有任何库存校验或二次确认提示。
- **风险**：库存告急的备件被继续领走，安全水位形同虚设。

### BUG-13 全局搜索框无结果反馈
- **位置**：顶栏搜索框「搜索设备 / 工单 / 预警，回车跳转台账」
- **现象**：placeholder 承诺「回车跳转台账」，但无输入建议、无结果下拉、无命中数提示；输入不存在的内容也没有"未找到"反馈。测试中输入后回车行为不确定。

### BUG-14 β 页面大量存在，带 β 标记的均为规划中
- **位置**：侧栏
- **现象**：带 β 的页面共 11 个：设备档案铭牌、预警规则阈值、异常检测、寿命预测 RUL、归因诊断、知识库助手、模型管理与对账、数据质量与漂移、数据集与特征。
- **问题**：直接访问这些路由（如 `#/equipment`）会落到兜底页「本页尚在规划中 / 该页面还没有实现」。**侧栏里 25 个入口中近一半点了没内容**，且兜底页措辞偏开发口吻（"该页面还没有实现"）。
- **额外坑**：路由命名与实际 hash 不一致 —— 手写 `#/equipment` 404，真实是 `#/assets`；`#/spare-requests` 404，真实是 `#/sreq`。

### BUG-15 审计日志/RBAC 页面只读且无实质数据支撑
- **位置**：`#/audit`、`#/rbac`
- **现象**：作为系统管理核心页，审计日志缺少可筛选的真实操作记录；RBAC 页面的角色权限映射与实际生效权限对不上（页面说 ADMIN_ALL 通吃，但角色表里未显式列出该组合的来源）。

## 3. 🟡 轻微问题（P2）

### BUG-16 设备「运行状态」与「已停止」计数矛盾
- `#/assets` 卡片：运行中 7 / 维修中 0 / 已停机 1 / 试运行 0，合计 8 ✔
- 但驾驶舱首页卡片：在管设备 8 / **正常运转 4** / 占比 50%。同一批设备"运行中 7"与"正常运转 4"对不上（94.7 分的设备显然不算故障），口径未说明。

### BUG-17 「平均健康度 94.7」在 8 台里只有 3 台有分的情况下的算法不透明
- 5 台未评估直接不计入平均，却把 94.7 当作全厂平均展示。应标注"（基于 3 台已评估设备）"，否则读者会误以为 8 台都很健康。

### BUG-18 健康度排行文案与数据相反
- 「后 3 名 · 重点关注」给出的分数是 94.7 并建议"维持正常监测"。既然后 3 名都如此健康，这个模块应当隐藏或改为"全厂健康度良好"。

### BUG-19 时间戳格式与年份不一致
- `#/sreq` 列表里时间是 `10-12 03:43`（缺年份），而申请号里嵌了完整日期 `SPR-20261012-0114`。跨年数据会歧义。工单页 `WO-20261012-4347` 同理。

### BUG-20 数据来源横幅占用版面过多且内容偏开发
- 每个页面顶部都有一条绿框「✓ 数据来源：真实接口 — A GET /api/v1/equipment?page=&size=」，末尾还写「bash scripts/start_all.sh」。这类内容对运维用户无意义，且每页重复，挤占首屏。建议折叠成一个小图标或"接口说明"。

### BUG-21 表格横向信息过载、数字缺少单位统一
- `#/spares` 表 9 列，`#/sreq` 表 11 列，横向拥挤。"在库量 / 可用量 / 已预留"三列在预留恒 0 时完全冗余。数值列（41 个 / 5 条 / 16 只）单位混在单元格里，无法排序或做数值格式化。

### BUG-22 「演示」按钮语义不明
- 顶栏 `🎬 演示` 按钮，未标注是"开始演示脚本"还是"演示模式"。点开前无从预期，误触可能打乱当前页面状态。

### BUG-23 告警铃铛恒为 0，但系统有预警体系
- 顶栏 `🔔 0` 始终为 0。驾驶舱首页「活跃预警 0 条 / 无严重预警」，而预警中心与预警规则阈值页配置齐全。**整个预警链路在演示数据下完全没有一条预警触发**，评审时看不出 B 服务的价值。

### BUG-24 兜底页文案与视觉过弱
- 未实现路由的兜底页只有一个"◐ 本页尚在规划中"，样式简陋、无返回引导、无相邻页面推荐，用户体验断崖。
