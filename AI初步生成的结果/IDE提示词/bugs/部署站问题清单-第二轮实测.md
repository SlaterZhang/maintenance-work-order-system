## 1. 🔴 严重问题（P0）

### P0-1 趋势外推枚举拼错，恶化趋势永远显示为 0 条

- **位置**：`web/js/pages/health.js:106-112`
- **页面**：健康评估中心 `#/health` →「指标趋势外推」卡片
- **现象**：页面显示「上行（RISING，恶化）**0 条** / 下行（FALLING，好转）**0 条** / 平稳·样本不足（UNKNOWN）**35 条**」。
- **反证（真实接口）**：`GET /b/api/v1/health-evaluations?pageSize=100` 返回 35 条，`trend` 字段**全部为 `DEGRADING`**：
  ```
  ('DEGRADING', 'EQ-000001') 24
  ('DEGRADING', 'EQ-000002') 5
  ('DEGRADING', 'EQ-000003') 6
  ```
- **根因**：后端枚举是 `DEGRADING / STABLE / IMPROVING / UNKNOWN`（`apps/fault-warning/src/domain/trend.py:139-143`），前端统计却筛不存在的 `RISING` / `FALLING`，故恒为 0，全部落进"平稳"。

  ```js
  // web/js/pages/health.js:106
  const trendUp   = evals.filter(e => e.trend === "RISING").length;   // ← 后端从不发这个值
  const trendDown = evals.filter(e => e.trend === "FALLING").length;  // ← 同上
  { label:"平稳 / 样本不足（UNKNOWN）", value: evals.length - trendUp - trendDown }
  ```

- **同仓已有正确写法可抄**：`web/js/charts.js:46-58` 的 `trendConclusionZh()` 正确使用 `IMPROVING / STABLE / DEGRADING`。同一份枚举两处写法不一致，属笔误。
- **影响**：这是"预测性维护"最核心的卖点展示位。演示时评委会看到"全厂趋势平稳"，而数据库里躺着 `predictedDaysToThreshold: 1.6`（EQ-000003 一天半后触阈值）却完全不报警。**建议列为第一优先修复项。**
- **修复方向**：`RISING → DEGRADING`、`FALLING → IMPROVING`，并把三档求和补一个"其它/UNKNOWN"兜底，避免新增枚举时再次静默归零。

### P0-2 同一设备健康度 94.7 与 30.6 同页并存，且缓存策略与新数据打架

- **位置**：驾驶舱首页 `/`（同页两张表）；`web/js/data.js:71-89, 106-109`
- **现象**：驾驶舱「设备实时状态」表：EQ-000001 健康度 **94.7**（绿）；同页下方「最新预警」表：同设备同故障，健康分 **30.6**（严重）。
- **接口事实**：
  - `GET /b/api/v1/warnings` → `WARN-20261012-0004`，`EQ-000001`，`healthScore 30.6`，`riskLevel CRITICAL`
  - `GET /b/api/v1/health-evaluations/latest?equipmentId=EQ-000001` → `healthScore 94.7`，`riskLevel LOW`，`evaluatedAt 2026-10-12T06:36:43Z`
- **根因**：`loadLatestEvaluations()` 用最新评估**整体覆盖** `healthMap`，并把状态硬编码成 `RESOLVED`：
  ```js
  // web/js/data.js:80-85
  state.healthMap[eq.equipmentId] = {
    score: latest.healthScore, riskLevel: latest.riskLevel,
    warningId: null, status: isHealthy(latest) ? "RESOLVED" : "OPEN",
    _t: Date.now(),          // ← 时间戳取"现在"，而非评估时间，导致永远压过预警
  };
  ```
  预警表读的是 `warning.healthScore`（历史快照，永不更新），实时状态表读的是 `latestEvaluation`。两者语义本就不同，但**页面上没有任何口径说明**，并排显示就是自相矛盾。
- **影响**：旧 BUG-01 的三页打架虽已收敛为"同页两个口径"，但演示时第一眼仍会被抓。**要么统一口径，要么在两个数字旁各标一句"（最新评估／预警触发时快照）"。**
- **修复方向**：短期加口径标注（成本最低）；长期让预警表显示"当前健康度"或明确灰化历史分。

### P0-3 备件「补货缺口」算法错误，且单位硬编码串味

- **位置**：`web/js/pages/spares.js:101-102, 128-129`
- **页面**：备件库存 `#/spares`
- **现象**：KPI「补货缺口 **11** / 3 项合计缺 11 个」。
- **实际数据**：三项低于安全库存——同步带 `5/15`、交流接触器 `4/10`、变频器 `2/3`。
  - 真实缺口 = (15−5) + (10−4) + (3−2) = **17**，而非 11。
  - 11 恰好是三项**可用量之和**（5+4+2），即"库里还剩多少"被当成了"还差多少"。
- **代码证据**：
  ```js
  // web/js/pages/spares.js:102
  const lowValue = low.reduce((s, p) => s + p.availableQuantity, 0);  // ← 累加的是可用量，不是缺口
  // :128
  + kpi("dim", "补货缺口", lowValue, low.length ? low.length + " 项合计缺 " + lowValue + " 个" : "无需补货")
  ```
- **次生问题**：文案硬编码单位"**个**"，但这三项单位分别是**条 / 个 / 台**（同步带-条、交流接触器-个、变频器-台），加总本身就不该有单位。
- **影响**：补货决策直接依赖这个数，少算 35%，且"个"字暴露了单位未做归一化。
- **修复方向**：改为 `s + (p.reorderPoint - p.availableQuantity)`；副标题去掉单位或改为"3 项合计缺口（跨品类，仅供排序参考）"。

## 2. 🟠 中等问题（P1）

### P1-1 「一键演示全链路」文案承诺 D 服务下发通知，代码里根本没有这一步

- **位置**：`web/js/data.js:231-244`（弹窗文案与实现同一函数）
- **现象**：点击顶栏「▶ 演示全链路」弹出确认框，明确写着：
  > `A` 写入异常样点（96.7℃ / 9.8 mm·s⁻¹）→ `B` 健康评分并创建预警 → `C` 按预警自动建工单 → **`D` 下发通知**
- **事实**：该函数最后一行只调 `injectData("abnormal", eq.equipmentId)`；`web/js/inject.js` 的注入流程只依次调 A、B、C 三个服务，**没有任何 D 服务调用**。而「系统集成监控」页自己承认 `C-INT-07 提交通知任务 = 无调用点`。
- **影响**：演示弹窗当着评委的面承诺了一个系统自己都标注"未接通"的能力。这是**主动制造**的信任缺口——不写这句就没事。
- **修复方向**：删掉「`D` 下发通知」，或改为「`D` 通知任务（C-INT-07 未接通，暂不投递）」。

### P1-2 「已闭环」KPI 口径易误读（含按契约闭环的 CANCELLED）

- **位置**：`web/js/pages/warns.js:38, 64`；页面 `#/warns`
- **现象**：KPI「已闭环 **10** / 10 条历史」，但表内实际是 **9 条 `RESOLVED` + 1 条 `CANCELLED`**；同页「严重 CRITICAL **0**」也与表内 10 条"严重"并列，易被读成矛盾。
- **判定**：CANCELLED 按契约（`apps/fault-warning/src/domain/enums.py:31-33`）确属**闭环终态**，逻辑**不算错**；但「严重 CRITICAL 0」只统计**活跃**预警，副标题「需立即处置」没点明"仅活跃"，与右侧 10 条历史严重预警并看即矛盾。
- **修复方向**：两个 KPI 的副标题补口径——"严重 CRITICAL（活跃）"、"已闭环（含工单取消回流 1 条）"。

### P1-3 全局搜索框只搜设备，却承诺搜"设备/工单/预警"

- **位置**：顶栏搜索框，placeholder =「搜索设备 / 工单 / 预警，回车跳转台账」
- **实测**：输入工单号 `WO-20261012-4085` 回车 → 跳转设备台账，并把该工单号**回填进设备搜索框**，结果必然 0 条。
- **影响**：placeholder 是明确的用户承诺，实际只实现了 1/3；且错误关键词被留在筛选框里，用户会以为"系统里没这张工单"。
- **修复方向**：要么按前缀识别（`WO-`→工单、`WARN-`→预警、`EQ-`→设备）分别跳转并高亮，要么把 placeholder 老实改成「搜索设备」。

### P1-4 侧栏「工单详情时间线」是死入口

- **位置**：侧栏「维修管理 → ◫ 工单详情时间线」`#/odetail`
- **现象**：从侧栏直接点击，页面只显示「请从工单列表或看板点击进入 / 缺少工单号」，**没有任何返回引导或工单选择器**。
- **影响**：11 个 β 页虽然标注了"演进中"，但这个入口连 β 标记都没有，点进去是一条断头路。
- **修复方向**：无 `orderId` 时展示"最近工单列表"让用户选，或直接从侧栏移除该入口（从列表/看板进入即可）。

### P1-5 备件「预留(RESERVE)」动作缺少身份分离校验

- **位置**：`apps/maintenance/src/application/spare_service.py:79-91`
- **现象**：`APPROVE` 与 `ISSUE` 都做了"申请人与操作人不能同一人"的硬约束（第 71、98 行），**唯独 `RESERVE` 没有任何身份校验**。
- **后果**：同一审批人可连续执行 `APPROVE → RESERVE` 两步；而页面在「为什么三方分离」里明确承诺"审批人不等于发料人""预留 ≠ 出库，账面与实物分开"。
- **影响**：治理设计的完整性有缺口——虽然最终发料仍需他人，但"审批+占库"由一人完成，与页面承诺的分离程度不符。
- **修复方向**：`RESERVE` 补充与 `req.approver_id` 的比对，或明确在页面注明"预留由审批人执行，视为审批动作的延续"。

### P1-6 RBAC 权限矩阵声明了一个服务端不存在的权限码 `NOTIFICATION_SEND`

- **位置**：`web/js/pages/rbac.js:61`、`web/js/enums.js:103`；页面 `#/rbac` →「角色权限矩阵」
- **现象**：矩阵表头标注"权限码 **21 项** × 角色 7 个"，其中"平台管理"分组列出三个码：`USER_ACCESS_READ`、`NOTIFICATION_SEND`、`ADMIN_ALL`。
- **反证**：D 服务（`apps/integration-quality/src/infrastructure/seed.py`）实际定义的权限码全集为 **20 个**，**不包含 `NOTIFICATION_SEND`**：
  ```
  ADMIN_ALL, USER_ACCESS_READ, EQUIPMENT_READ, EQUIPMENT_MANAGE, TELEMETRY_READ,
  TELEMETRY_WRITE, WARNING_READ, WARNING_ACKNOWLEDGE, WORK_ORDER_READ, WORK_ORDER_CREATE,
  WORK_ORDER_CONFIRM, WORK_ORDER_ASSIGN, WORK_ORDER_ACCEPT, WORK_ORDER_MAINTAIN,
  WORK_ORDER_INSPECT, WORK_ORDER_CANCEL, SPARE_READ, SPARE_REQUEST, SPARE_APPROVE, SPARE_ISSUE
  ```
- **后果**：该行的"持有角色"计数恒为 0（无任何角色持有这个码），矩阵里挂着一行永远为空、且服务端永远不会校验的权限。这与本页"权限码由 D 服务按角色展开"的自述直接冲突。
- **修复方向**：删除 `NOTIFICATION_SEND`（并在 `enums.js` 的中文映射里一并清理），表头计数改为 20；若确实需要"通知发送"能力，则应在 D 服务补该权限码并授予相应角色。

### P1-7 健康评估中心「今日评估 11 / 累计 35」与「LOW 3 / 占比 100%」口径割裂

- **位置**：`#/health` 顶部 KPI
- **现象**：同一组 KPI 里，「今日评估 **11**」是**今日新增条数**，「LOW（正常）**3** / 占比 100%」是**按设备去重后的当前状态**（3 台已评估设备全为 LOW），两个数字的基数不同却并排放置。
- **影响**：读者会自然算"11 条里 3 条 LOW，那其余 8 条呢"，实际是 11 条今日记录全都属于这 3 台设备。同页「全厂健康度总览」标注了"8 台设备 / 3 台已评估"，信息是齐的，但 KPI 区没写清。
- **修复方向**：把"LOW 3"的副标题从"占比 100%"改为"3 台已评估设备 · 占比 100%"。

## 3. 🟡 轻微问题（P2）

### P2-1 死代码：`dashboard.js`、`equipment.js` 与 `web/dashboard.html` 无任何引用

- **位置**：`web/js/dashboard.js`（6.0 KB）、`web/js/equipment.js`（16.9 KB）、`web/dashboard.html`、`web/prototype/platform.html`（200 KB）
- **证据**：`web/index.html` 的 `<script>` 清单（第 74–104 行）**不包含** `dashboard.js` 与 `equipment.js`（`orders.js`、`modals.js`、`charts.js` 均在列，不受影响）；全仓无任何文件引用 `dashboard.html` 或 `prototype/`。
- **影响**：`equipment.js` 里的 `trendConclusionZh()` 等函数与在用版本重复，后续维护极易改错文件（**P0-1 就是同类"两份枚举写法不一致"的翻版**）。新人（或下一个 AI）改到孤儿文件上会白干。
- **修复方向**：删除或移入 `web/legacy/` 并在 README 注明不再加载。

### P2-2 大屏每 5 秒发 16 个请求，无批量接口

- **位置**：`web/js/pages/screen.js:208-212`
- **证据**：`poll()` 每 5 秒执行 `Promise.all([loadLatestEvaluations(), loadWarnings(), loadLatestTelemetry()])`；其中前两者各按设备逐台请求 8 次 ⇒ 每轮约 **16 个请求**。本轮实测捕获 `health-evaluations/latest` 被调用 **120 次**、单台遥测各 15 次。
- **页面已自述**这一点（"8 台可行；上千台时应新增聚合接口"），属**已知设计取舍**。但演示环境单机四服务，5 秒 16 请求的轮询噪声会淹没集成监控页的"事件投递记录"，也让延迟数字失真。
- **修复方向**：大屏轮询间隔放宽到 15–30 秒，或为 A/B 增加批量取数接口。

### P2-3 演示库残留"验证/演示"字样的测试工单与申请

- **位置**：工单列表 `#/orders`、备件领用 `#/sreq`
- **实测数据**：
  - 工单：`WO-20261012-4085 验证备件三方分离`（待确认）、`WO-20261012-6379 验证三方分离`、`WO-20261012-9341 / 8520 验证自审拦截`、`WO-20261012-4347 演示：主轴异响`
  - 领用申请：`SPR-20261012-5542 / 7657 / 6303 / 1400 / 7038` 等 **8 条「已驳回」**，均为 USER-D-001 自审测试产物，且多条内容完全相同、时间集中在 04:24–04:56。
- **影响**：侧栏「工单列表 **1**」的角标就是那张"验证备件三方分离"；领用页 16 条里 8 条是驳回的测试垃圾，把真实业务流淹没。演示前建议清库重建（`reset_demo.py`）或把这些单据改名/删除。

### P2-4 多台设备遥测值完全相同，暴露种子数据是复制粘贴

- **实测**：EQ-000001 / EQ-000002 / EQ-000003 最新样点**完全一致**——`65.2℃ / 3.4 mm·s⁻¹ / 11.7 A / 1450 rpm`，而三者的 `measuredAt` 分别是 10-12 / 10-07 / 10-08。
- **影响**：三台设备在台账、大屏、异常检测页数值一模一样，一眼可看出是同一份种子数据复制的。更进一步，这条"完全相同"的样点恰好是**唯一越线（振动 3.4 > 3.0）**、被 B 判为"主轴轴承振动异常"、并在多处展示为"主要风险指标"的数据——三台设备顶着同一个故障描述。
- **修复方向**：为每台设备生成有差异的遥测基线（哪怕只是随机扰动）。

### P2-5 多页把内部欠账与源码路径直接展示给终端用户

- **现象**（合同一处）：
  - `#/notify`：整页自述 `B 无 enqueue 调用点`、`C 无调用点`，并列出 `apps/fault-warning/src/application/event_dispatch.py:94` 等源码路径。
  - `#/integ`：「C-INT-07 … 无调用点」+ 源码路径。
  - `#/health`、`#/assets`：标注评分口径时给出 `apps/fault-warning/src/domain/scoring.py`。
  - 每页顶部绿色横幅均写「bash scripts/start_all.sh」。
- **判定**：这些标注**内容属实**（本轮已逐条用代码复核，未发现虚假描述），"如实标注边界"的态度值得肯定。但对运维观众而言，源码路径与部署命令属于开发者语汇，占据首屏且每页重复。
- **修复方向**：保留"未接通"的事实说明，但把源码路径与 `start_all.sh` 收进折叠的「接口说明」里（该横幅已有折叠控件，把路径挪进去即可）。

## 4. 建议的修复优先级
